# KMS Key Resolution

## Status

Proposed

## Context

`EncryptData` and `DecryptData` need an AES key. The caller can either provide the raw key or provide a key ID that the Crypto Broker resolves through a KMS.

KMS-backed key resolution will also be used for certificate signing, allowing the CA private key to be referenced by key ID instead of being supplied directly with each request.

The Crypto Broker does not create, import, rotate, list, or delete KMS keys. Key lifecycle management remains the responsibility of the KMS and the operator.

The KMS currently resolves only the encryption key. The caller always provides the nonce and optional AAD for encryption, and the nonce, optional AAD, and authentication tag for decryption.

## Decision

`EncryptData` and `DecryptData` use `KeySource`:

```proto
message KeySource {
  oneof source {
    string keyId  = 1;
    bytes  rawKey = 2;
  }
}
```

The implemented behavior is:

| Key source | Behavior |
| --- | --- |
| `rawKey` | Use the supplied bytes and validate their length against the profile. |
| `keyId` | Resolve the key through the KMS client configured in the profile, then validate its length. |
| No source | Reject the request. |

`keyId` requires both `KMS.Client` and `KMS.Config`. `rawKey` can also be used when the profile contains a KMS configuration.

KMS resolution currently applies only to `EncryptData` and `DecryptData`. OpenBao KV v2 is the only implemented KMS client.

## Profile Configuration

KMS is configured per profile:

```yaml
- Name: Default
  KMS:
    Client: openbao
    Config: openbao.yaml
    Cache: false
  Settings:
    CryptoLibrary: native
  API:
    EncryptData:
      EncryptAlg: aes-gcm
      KeySize: 256
```

| Field | Description |
| --- | --- |
| `Client` | KMS client implementation. Currently only `openbao` is supported. |
| `Config` | KMS client configuration file inside `CRYPTO_BROKER_KMS_DIR`. |
| `Cache` | Enables in-memory key caching. It is optional and defaults to `false`. |

The KMS client is loaded lazily on the first request using `keyId`. One client is retained and reused for each profile.

## KMS Configuration Directory

`CRYPTO_BROKER_KMS_DIR` contains KMS client configuration files:

```bash
export CRYPTO_BROKER_KMS_DIR="/etc/crypto-broker/kms"
```

The directory may be an absolute path or a path relative to the server process's working directory. It must be set when KMS-backed key resolution is used. The server has no built-in default; `configs/` in `.env.example` is only an example value.

`KMS.Config` is resolved inside this directory. For example:

```text
CRYPTO_BROKER_KMS_DIR=/etc/crypto-broker/kms
KMS.Config=openbao.yaml
result=/etc/crypto-broker/kms/openbao.yaml
```

The server uses `os.OpenRoot` so `KMS.Config` cannot escape `CRYPTO_BROKER_KMS_DIR`. Absolute configuration paths and `../` path traversal are rejected.

## Key Cache

Caching is disabled by default:

```yaml
Cache: false
```

With caching disabled, every request using `keyId` retrieves the key from the KMS. The KMS client itself is still reused.

When `Cache: true`:

* keys are cached in server memory for 60 minutes;
* the cache is local to one server process;
* keys are cached per profile and key ID;
* copies of key byte slices are stored and returned; and
* the TTL is fixed and is not currently configurable.

Caching reduces KMS calls but keeps key material in memory longer. It may also keep using an old value for up to 60 minutes after a key is changed in the KMS.

## OpenBao

The OpenBao client configuration is YAML:

```yaml
address: https://openbao.example.com
token: <OpenBao token>
mount: keys2
```

For `keyId: secret_1`, the client reads the KV v2 path:

```text
keys2/data/secret_1
```

The secret must contain a `key` field under the KV v2 response data. Its value must be a hexadecimal string without a `0x` prefix:

```yaml
key: 67e1befda6538f162a308bb37b922441bed6e27039a26a48ad8e11c568c4cda0
```

The client decodes the hexadecimal value to bytes. `EncryptData` and `DecryptData` then verify that its length matches `API.EncryptData.KeySize`.

The OpenBao token and configuration file must be protected as secrets.

## Errors

Using `keyId` without a complete KMS profile configuration returns a gRPC `FailedPrecondition` error. Configuration, connection, missing-key, response-format, hexadecimal-decoding, and key-length failures return contextual errors from the relevant layer.

There is currently no public KMS-specific sentinel error set.

## Extending KMS Support

The internal KMS interface is:

```go
type Client interface {
    GetKey(keyID string) ([]byte, error)
}
```

Adding another KMS currently requires a new Go implementation, an entry in the server's client-selection logic, and a server rebuild and deployment. Runtime plugins, uploaded adapters, and an adapter sidecar protocol are not implemented.

## Consequences

* Callers use one request model for raw and KMS-resolved keys.
* Profiles select the KMS client and control the required encryption key size.
* KMS configuration files are confined to an operator-selected directory.
* Key lifecycle management stays outside the Crypto Broker.
* The broker handles plaintext symmetric keys in memory.
* Enabling caching increases key-retention time and may temporarily use stale keys.
* KMS authorization is controlled by KMS credentials and policies; the broker does not map key IDs per application.

## Rejected Options

### Key Lifecycle API

The Crypto Broker will not expose APIs for creating, importing, rotating, listing, or deleting KMS keys because these operations are backend-specific and already belong to the KMS.

### Backend-specific APIs

The Crypto Broker will not expose a different API for every KMS backend because callers should not need to change when the configured backend changes.
