# Key Resolution for KMS-backed Crypto Broker Operations

## Status

Proposed

## Context and Problem Statement

The Crypto Broker Server supports cryptographic operations through profiles. Depending on the selected profile, key material may be supplied with each request or be managed by the key management system (KMS) configured for that profile.

ADR 0011 established that broker-managed cryptographic material is handled through a pluggable KMS abstraction layer. This ADR defines how an individual cryptographic request selects its key material.

There is no end-user API for creating, importing, listing, deleting, or otherwise managing keys. Key lifecycle management remains the responsibility of the configured KMS or the operator's provisioning process.

Cryptographic requests must support both of these cases:

* The caller supplies the key material directly with the request.
* The caller supplies a `keyID`, and the broker resolves and uses the key from the KMS configured by the selected profile.

The broker must preserve profile-based control of cryptographic algorithms and backend configuration while ensuring that callers cannot use another application's key.

## Decision Drivers

* Keep cryptographic operation APIs simple for callers
* Support caller-managed and KMS-managed keys in the same operation flow
* Keep key lifecycle management out of the Crypto Broker's end-user API
* Keep KMS-specific identifiers and configuration hidden from callers
* Ensure that the profile determines the permitted algorithm and key characteristics
* Avoid exposing KMS-returned private key material to callers
* Allow new KMS backends to be added without changing callers
* Ensure that applications can use only their own KMS-managed keys

## Considered Options

* Expose a key lifecycle API from the Crypto Broker
* Expose backend-specific KMS APIs directly
* Resolve caller-provided key IDs transparently during cryptographic operations

## Decision Outcome

Chosen option: **Resolve caller-provided key IDs transparently during cryptographic operations**.

Each cryptographic request contains either direct key material or a `keyID`.

```text
request contains key material  -> broker validates and uses the supplied material
request contains keyID         -> broker resolves the key in the profile's configured KMS
```

When a request contains a `keyID`, the broker:

1. validates the selected profile and requested cryptographic function
2. verifies that the profile has a KMS configured
3. resolves the `keyID` to the KMS-specific key reference for the selected profile and authenticated application;
4. calls the configured KMS backend using that reference, retrieves the required key material into Crypto Broker memory, and performs the cryptographic operation; and
5. clears temporary key buffers where practical after the operation.

A `keyID` may be an opaque Crypto Broker identifier that maps to a KMS-specific key reference. Profiles may instead permit a KMS-specific identifier when that is appropriate for the configured backend and authorization model.

## Request Key Selection

The request model for every operation that requires a key must express one mutually exclusive key source:

```proto
message KeySource {
  oneof source {
    string keyId  = 1;
    bytes  rawKey = 2;
  }
}
```

Exactly one field in `KeySource.source` must be set.

| Request content | Broker behavior |
| --- | --- |
| `rawKey` is set | Validate the material against the selected profile and function, then perform the operation using caller-supplied key material. |
| `keyId` is set | Resolve the key ID for the authenticated application, retrieve the referenced key from the profile's KMS into broker memory, and perform the operation. |
| Both are set | Reject the request as invalid. |
| Neither is set | Reject the request as invalid. |

The exact request structure may vary by operation, but it must retain these semantics.

`rawKey` contains caller-supplied key material. The selected profile and function determine its required representation, algorithm, size, curve, and permitted usage; the broker validates the supplied bytes accordingly.

## Profile and KMS Resolution

The selected profile determines:

* whether KMS-backed key resolution is supported
* which KMS backend is used
* the KMS adapter configuration file to use

For example:

```yaml
name: default-profile

kms:
  type:   openbao
  config: openbao-config.json
```

The `kms.config` value identifies the adapter configuration file. All KMS adapter configuration files are stored in one designated configuration directory, making them easy for operators to locate and maintain. The broker resolves `kms.config` within that directory.

Every KMS adapter must read and validate its configured file before it is used. The adapter owns the configuration schema and interprets the file according to its KMS backend; the broker only selects the adapter and provides the configured file location.

## Error Handling

The broker exposes stable broker errors rather than raw backend errors. Relevant errors include:

```go
var (
  ErrKMSNotConfigured = errors.New("KMS not configured")
  ErrKMSConfiguration = errors.New("KMS invalid configuration")
  ErrKMSUnavailable   = errors.New("KMS backend unavailable")
  ErrKMSKeyNotFound   = errors.New("KMS key not found")
)
```

## Security Requirements

* Private and symmetric key material must never be logged.
* Caller-supplied key material must not remain in memory longer than necessary; temporary buffers should be cleared where practical.
* Private and symmetric key material retrieved from a KMS must be held in Crypto Broker memory only for as long as needed to perform the operation; temporary buffers should be cleared where practical.
* When the broker issues opaque `keyID` values, they must not reveal the underlying KMS identifier.
* Backend errors and identifiers must not be exposed to callers when doing so would reveal sensitive implementation details.

## Extending KMS Adapters

The KMS abstraction must permit new adapters to be added. The following delivery models are considered for adapters that are not included with the Crypto Broker distribution.

Regardless of delivery model, every adapter must read and validate the configuration file selected by `kms.config` from the common KMS configuration directory.

### 1. Contribute an Adapter by GitHub Pull Request

An adapter is implemented against the broker's KMS interface, submitted as a GitHub pull request, reviewed, and merged into the Crypto Broker codebase.

**Pros:**

* The adapter is reviewed, tested, versioned, and released with the broker.
* It has no additional runtime deployment or network hop.

**Cons:**

* Users depend on the maintainers' review and release cycle.
* It is not suitable for private or organization-specific adapters that cannot be upstreamed.

### 2. Run an Adapter Sidecar

An organization runs a small adapter service next to the Crypto Broker. The broker communicates with it over a defined protocol, and the sidecar communicates with the target KMS.

**Pros:**

* The adapter can use its own language, dependencies, and release cycle.
* It isolates adapter failures and dependencies from the broker process.

**Cons:**

* It adds a service, network latency, operational configuration, and Kubernetes deployment work.
* Users must implement, build, secure, and operate the sidecar themselves.

### 3. Upload a Go Plugin (`.so`)

An organization implements an adapter against the broker's KMS interface, compiles it as a Go plugin, and uploads the resulting `.so` file through an `UploadAdapter` endpoint. Before loading the plugin, the broker validates its metadata and compatibility with the broker build, including the required Go version and build flags.

**Pros:**

* It avoids a separate service and network hop.
* Organizations can add private adapters without waiting for an upstream release.
* A new adapter can be uploaded and made available without rebuilding, redeploying, or restarting the broker.

**Cons:**

* A plugin executes code in the broker process. This trust boundary is acceptable only because compilation and upload are managed by the operator that owns the Crypto Broker deployment.
* Go plugins are tightly coupled to the broker build, Go version, platform, and dependency versions; compatibility validation cannot make an incompatible plugin safe to load.

## Consequences

* Good, because callers use one key-selection model across KMS backends.
* Good, because the broker has no end-user key lifecycle API to maintain.
* Good, because operators can use native KMS provisioning workflows.
* Good, because profiles continue to control permitted cryptographic parameters.
* Good, because opaque broker IDs can hide KMS-specific key references when that is required.
* Bad, because profiles using opaque broker IDs require the broker to persist or reconstruct mappings to KMS-specific references.
* Bad, because the KMS or operator workflow must provide lifecycle management outside the broker.
* Bad, because the Crypto Broker must securely handle KMS-returned private and symmetric key material in memory while performing operations.
* Bad, because supporting and managing adapters for different KMS backends adds implementation and operational complexity to the Crypto Broker.

## Rejected Options

### Expose a Key Lifecycle API from the Crypto Broker

The broker would create, import, list, and delete keys through an end-user API.

This was rejected because key provisioning is not part of the intended Crypto Broker end-user interface. It would duplicate backend lifecycle capabilities and require the broker to own lifecycle semantics that vary between KMS backends.

### Expose Backend-Specific KMS APIs Directly

Each backend would expose its own operations and request structures.

This was rejected because callers would need backend-specific knowledge, profiles would no longer provide a stable abstraction, and switching KMS backends would require application changes.
